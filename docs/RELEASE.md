# قائمة النشر

كل نشر يمر بهذه الخطوات بالترتيب. `scripts/deploy.sh` ينفّذ السحب وبوابة الاختبارات والبناء والتشغيل؛ والباقي يدوي.

## قبل النشر

1. **وسم نقطة الرجوع:**
   ```bash
   cd /opt/nuskJO
   NAME=<اسم قصير للتغيير>; DATE=$(date +%Y%m%d)
   docker run --rm -v "$PWD":/repo -w /repo alpine/git tag "backup/pre-$NAME-$DATE"
   docker tag nuskjo-nuskjo-app:latest "nuskjo-nuskjo-app:backup-pre-$NAME"
   ```
2. **نسخة يدوية وسحبها مشفّرة:**
   ```bash
   docker exec -u www-data nuskjo-app php artisan backup:run --reason=manual --label="pre-$NAME"
   bash scripts/backup/collect.sh
   ```
3. **إن كان في التغيير هجرات:** ابنِ الصورة المرشّحة وجرّب هجراتها على بيانات اليوم دون لمس الإنتاج:
   ```bash
   docker compose build --build-arg GIT_COMMIT=$(docker run --rm -v "$PWD":/repo -w /repo alpine/git rev-parse --short HEAD) nuskjo-app
   docker tag nuskjo-nuskjo-app:latest nuskjo-nuskjo-app:candidate
   DRILL_IMAGE=nuskjo-nuskjo-app:candidate bash scripts/backup/drill.sh --rehearse
   ```
   فشلها يعني: لا تنشر.
4. اقرأ «ملاحظات الترقية» للإصدار في [CHANGELOG.md](../CHANGELOG.md).

## النشر

```bash
bash scripts/deploy.sh
```
يشغّل الاختبارات في حاوية بلا شبكة قبل البناء، ويتوقف إن فشلت. عند الإقلاع يأخذ التطبيق نسخة تلقائية قبل أي هجرة معلّقة (`BACKUP_PRE_MIGRATE=true`) ويرفض الهجرة إن فشلت النسخة.

**الصلاحيات الجديدة تصل بهجرات فقط.** لا تشغّل `RolePermissionSeeder` على الإنتاج: يعيد مزامنة صلاحيات الأدوار فيمسح ما خصّصه المدير. في الطوارئ: `docker exec -it nuskjo-app php artisan auth:restore-admin <البريد> --reset-password`.

## بعد النشر

- `docker ps` يُظهر الحاوية healthy (الفحص على `/up`).
- `docker exec -u www-data nuskjo-app php artisan migrate:status` بلا Pending.
- صفحة النسخ الاحتياطي: الأعداد معقولة وآخر نسخة (pre-migrate إن وُجدت هجرات) ناجحة.
- السطر `deployed` في `/opt/nuskJO-deploy.log`.

## التراجع

## فصل حجم القاعدة (مرة واحدة)

قبل الفصل، حجم القاعدة يغطي مجلد `database/` كله فيحجب ملفات الهجرات في الصورة الجديدة (فكانت تُنسخ يدوياً بـ docker cp). بعده تعيش القاعدة وحدها في `database/data/` على الحجم `nuskjo_nuskjo-dbdata`.

حين يصل تغيير `docker-compose.yml` الخاص بالفصل، يتوقف `scripts/deploy.sh` بعد البناء ويطلب هذه الخطوات بدل الإقلاع على حجم فارغ:

```bash
cd /opt/nuskJO
M=scripts/backup/move-db-volume.sh
ARGS="--compose-dir /opt/nuskJO --project nuskjo --service nuskjo-app --old nuskjo_nuskjo-database --new nuskjo_nuskjo-dbdata"
bash $M $ARGS --check-only     # (أ) هجرات ستعمل عند الإقلاع، (ب) هجرات دخلت بـ docker cp ولم تُحفظ، (ج) نسخ قديمة في الحجم (تُشفَّر ولا تُحذف)
bash $M $ARGS                  # في نافذة هادئة: نسخة وسحب مشفّر، إيقاف، نسخ القاعدة، مقارنة الأعداد، إقلاع، فحص
```

الحجم القديم يبقى كما هو 30 يوماً على الأقل. الرجوع (يحمل معه ما كُتب بعد التبديل): `bash $M $ARGS --reverse`، ثم `git revert` لتغيير الحجم في `docker-compose.yml` و`docker compose up -d nuskjo-app`. السكربت نفسه يعمل لمشاريع أخرى بالتخطيط نفسه بتغيير `--compose-dir --project --service --old --new`؛ وابدأ بالأقل أهمية.

## إطلاق حارس الصلاحيات (مرة واحدة)

1. قبل النشر: `AUTHZ_MODE=log` في `.env.production`. الافتراضي في الكود الرفض.
2. انشر كالمعتاد. يُفرض فوراً حتى في وضع التسجيل: الاعتماد والرفض، وفتح المعتمد للتعديل والحذف (للمدير)، وإدارة المستخدمين والأدوار والإعدادات، وإقفال الفترات.
3. أسبوعاً، يومياً: `docker exec -u www-data nuskjo-app php artisan authz:report --hours=24`. كل «would_deny» لموظف يحتاج الصفحة فعلاً: امنح دوره الصلاحية من **الإعدادات › الصلاحيات** (لا بالـ seeder). و«unmapped» تعني مساراً جديداً نُسي إعلان صلاحيته في routes/web.php: أصلحه في الكود.
4. ثم احذف المتغير (أو `AUTHZ_MODE=enforce`) و`docker compose up -d nuskjo-app` لإعادة `config:cache`.

## إطلاق نطاق صندوق الواتساب (مرة واحدة)

بعده يرى الموظف بلا «رؤية كل المحادثات» ما يحمل وسماً من اختصاصه أو ما وُكّل له فقط.
1. قبل النشر: املأ **الواتساب › توجيه المواضيع** بمختص أساسي لكل موضوع، وامنح `whatsapp.view_all` لمن يوزّع المحادثات، وقرّر من يُمنح `whatsapp.admin_chats` (محادثات أرقام الإدارة؛ دور المدير يملكها تلقائياً).
2. انشر، ثم الهجرة `2026_10_14_000005` باسم www-data. امنح `whatsapp.admin_chats` للأدوار المقررة من **الإعدادات › الصلاحيات**.
3. `docker exec -u www-data nuskjo-app php artisan whatsapp:fence-report`: كل موظف في «لا يرون أي محادثة» يحتاج اختصاصاً أو توكيلاً. أرسل للموظفين: حدّثوا الصفحة.
4. بعد يومين أو ثلاثة بلا شكاوى: أعد التقرير، ثم `WA_FENCE_QUOTES=true` في `.env.production` و`docker compose up -d nuskjo-app`.

## ترقية إصدار Graph (عند كل إصدار جديد)

التنبيه اليومي يبدأ قبل 60 يوماً من نهاية الإصدار، واللوحة في **إعدادات الواتساب › 🧭 الإصدارات والحماية** تعرض الحالة.
1. `docker exec -u www-data nuskjo-app php artisan whatsapp:graph-smoke --target=<الإصدار الهدف> --media` (قراءة فقط).
2. `WA_GRAPH_VERSION=<الهدف>` في `.env.production` ثم `docker compose up -d --force-recreate nuskjo-app`. جرّب نصاً وصورة وصوتاً وحالات التسليم، وراقب 48 ساعة.
3. بعدها ارفع إصدار حقول الويبهوك في App Dashboard › WhatsApp › Configuration، واكتب `WA_WEBHOOK_VERSION` بالقيمة نفسها، وأرسل رسالة واردة من هاتف اختبار.
4. التراجع: الإصدار السابق في `WA_GRAPH_VERSION` ثم force-recreate (يصلح حتى تاريخ نهايته فقط).

فحص مضيف الوسائط: أسبوع بـ `WA_MEDIA_HOST_MODE=log` بلا «WA media host outside allowlist» ولا «sha256 mismatch» في السجل، ثم `enforce`.
appsecret_proof (اختياري): `WA_APPSECRET_PROOF=true` أسبوعاً بلا APPSECRET_PROOF_INVALID، والتأكد أن لا مستهلك آخر لرموز التطبيق، ثم «Require App Secret» في اللوحة. التراجع: ألغِ الخيار في اللوحة أولاً ثم أطفئ المتغير.

## الأسرار خارج الصورة (مرة واحدة، قبل أول نشر لها)

1. **قبل النشر** طابق بصمة المفتاح الفعّال ببصمة الملف (8 خانات، لا المفتاح):
   `docker exec nuskjo-app php -r '$c=require "/var/www/html/bootstrap/cache/config.php"; echo substr(hash("sha256",$c["app"]["key"]),0,8);'`
   و`grep '^APP_KEY=' /opt/nuskJO/.env.production | cut -d= -f2- | tr -d '"\r' | sha256sum | cut -c1-8`.
   إن اختلفتا فالمفتاح الفعّال مخبوز في الصورة: انقله إلى `.env.production` قبل النشر، وإلا لن تُقرأ الإعدادات المشفّرة. واحفظ المفتاح في مدير كلمات المرور.
2. انشر. الإقلاع يرفض الآن مفتاحاً لا يُفك إلى 32 بايتاً أو `APP_DEBUG=true` (`BOOT_GUARD=warn` للطوارئ)، ويطبع بصمة المفتاح فقط. `docker compose logs nuskjo-app | grep fingerprint` يجب أن يطابق البصمة أعلاه، و`whatsapp:doctor` يطبع ملاحظات الصحة.
3. البناء يمر بـ `docker/check-context.sh` (ضمن deploy.sh)، وVITE_* تصل الواجهة كسرّ بناء. تحقق: `docker run --rm --entrypoint sh nuskjo-nuskjo-app -c 'ls -a /var/www/html | grep "^\.env"'` فارغ، وجرس الإشعارات اللحظي يعمل.

## ربط المنفذ على loopback (مرة واحدة)

1. تأكد: `docker version` 28 أو أحدث، ولا أحد يطرق 4020 مباشرة غير بوابة شبكة الحاوية (سجل nginx في `docker compose logs`)، وسجّل البوابة: `docker network inspect nuskjo_default -f '{{range .IPAM.Config}}{{.Gateway}}{{end}}'`.
2. غيّر قاعدة النفق لـ nuskjo وحدها في Zero Trust إلى `http://127.0.0.1:4020` (النفق مشترك بين المشاريع: لا تستبدل قائمة ingress كلها).
3. أنشئ `/opt/nuskJO/.env` (لتعويض compose لا للتطبيق) فيه `NUSKJO_BIND_ADDRESS=127.0.0.1`، ثم `docker compose up -d nuskjo-app`. تحقق: `ss -ltnp | grep 4020` يعرض 127.0.0.1 فقط، والموقع والدخول والجرس اللحظي وويبهوك ميتا وبطاقات العروض تعمل.
4. بعد يوم مستقر: `TRUSTED_PROXIES=127.0.0.1,<البوابة>/32` في `.env.production` ثم `up -d`. تحقق: آخر صفوف `audit_logs.ip_address` عناوين عامة، والحضور بالشبكة يعمل، ولا `proxy.untrusted_forwarded` في السجل، و`whatsapp:doctor` بلا TRUST_ALL_PROXIES.
5. التراجع: احذف السطر من `/opt/nuskJO/.env` ثم `up -d`، وأعد قاعدة النفق.

## موثوقية رد الواتساب (مرة واحدة، على مراحل)

**النشر الأول (الوظيفة والهجرة `2026_10_14_000007` وWAL وفصل الطابور معاً):**
1. نسخة: `docker exec -u www-data nuskjo-app php artisan backup:run --reason=manual --label=pre-e07`.
2. أوقف التقاط وظائف جديدة واترك الجارية تنتهي: `docker exec -u www-data nuskjo-app php artisan queue:pause database:default`، ثم انتظر حتى يصير `docker exec -u www-data nuskjo-app sqlite3 /var/www/html/database/data/database.sqlite "SELECT count(*) FROM jobs WHERE reserved_at IS NOT NULL"` صفراً (دقيقتان على الأكثر).
3. انشر، ثم **فوراً** `docker exec -u www-data nuskjo-app php artisan queue:continue database:default`. الإيقاف محفوظ في كاش القاعدة فيبقى بعد النشر، وبدون هذا الأمر لا تُرسل الإشعارات. ما بقي من ردود في default يعالجه عامل default مرة واحدة.
4. تحقق: `PRAGMA journal_mode` يرجع `wal` (docs/RESTORE.md «WAL»)، و`supervisorctl status` داخل الحاوية يعرض `laravel-wa:laravel-wa_00` و`laravel-queue` يعملان، و`php artisan whatsapp:reliability` يعرض الأعلام.

**الأعلام بعدها، كلٌّ وحده** (`docker exec -u www-data nuskjo-app php artisan whatsapp:reliability <العلم> on|off`):
- `reconcile` بعد أسبوع هادئ، وبعد أن تبدو قائمة `whatsapp:reconcile-replies --dry-run` منطقية.
- `webhook_5xx` بعد WAL فقط.
- التراجع: `off` للعلم نفسه، بلا نشر.

**الرجوع عن فصل الطابور:** `WA_REPLY_QUEUE=default` في `.env.production` ثم `docker compose up -d nuskjo-app`، ثم صرّف ما بقي: `docker exec -u www-data nuskjo-app php artisan queue:work database --queue=wa-replies --stop-when-empty`.

**عامل رد ثانٍ (`numprocs=2` لـ laravel-wa وحده)**، وفقط إن تحققت كل الشروط:
- مرّ أسبوع كامل بعد WAL وفصل الطابور.
- `grep -c "database is locked"` على `storage/logs/laravel*.log` و`storage/logs/queue-*-error.log` يعطي صفراً.
- لا صفوف ProcessWhatsAppReply جديدة في `failed_jobs`.
- `docker stats nuskjo-app` يترك هامشاً للعامل الإضافي (نحو 60–80MB).

بعد رفع العدد: راقب «database is locked» 72 ساعة، وقِس في الذروة الزمن من `jobs.available_at` إلى بدء التنفيذ. للتراجع: `numprocs=1` ثم إعادة النشر.

لا تنشر أثناء نسخة يدوية جارية من صفحة النسخ: عامل default ينتظر 40 ثانية فقط عند الإيقاف.

## فحص الصحة وتنبيهات ميتا (مرة واحدة، على مراحل)

العلَمان في `/opt/nuskJO/.env` (ملف تعويض compose، لا `.env.production`)، وكل تغيير بعده `docker compose up -d nuskjo-app`.

1. **نشر صامت:** انشر كالمعتاد؛ العلَمان مطفآن، والهجرة `2026_10_14_000008` تعمل في الإقلاع. تحقق:
   - `docker exec -u www-data nuskjo-app php artisan ops:status`: نبضة المجدول ونبضتا العاملين أحدث من دقيقتين.
   - `docker exec -u www-data nuskjo-app php artisan schedule:list | grep -E "ops:|credentials|health-status"`.
2. **فحص الصحة:** `OPS_HEALTH_CHECKS=true` ثم `up -d`. تحقق:
   - `docker exec nuskjo-app curl -fsS -o /dev/null -w '%{http_code}\n' localhost:4020/up` يطبع 200.
   - بعد دقيقتين، `docker inspect -f '{{.State.Health.Status}}' nuskjo-app` يطبع healthy.
   - في وقت هادئ: `docker exec nuskjo-app supervisorctl stop laravel-queue`. خلال 7 دقائق تقريباً تصير الحالة unhealthy ويصل إشعار واحد «⛔ العامل الخلفي متوقف». ثم `supervisorctl start laravel-queue`.
3. **فحوص ميتا:** أدخل App ID في **الواتساب › الإعدادات › ربط قناة ميتا** (App settings › Basic في لوحة ميتا)، ثم `WA_META_CHECKS=true` و`up -d`. شغّل يدوياً:
   - `docker exec -u www-data nuskjo-app php artisan whatsapp:credentials-check`
   - `docker exec -u www-data nuskjo-app php artisan whatsapp:health-status`
   راجع بطاقة «🩺 صحة النظام والقناة». إن ظهر «معرّف التطبيق أو سرّه خطأ»، فتأكد أن App Secret المحفوظ للتطبيق نفسه الذي وُلّد منه رمز مستخدم النظام.
4. **المراقب الخارجي:** حين تتوقف القاعدة أو الحاوية كلها لا يستطيع التطبيق التنبيه. يطرق المراقب `https://nuskjo.grade.sbs/up` كل 5 دقائق ويرسل بريداً عند الفشل. لا يرى إلا up أو down.

**التراجع:** `OPS_HEALTH_CHECKS=false` و/أو `WA_META_CHECKS=false` ثم `up -d`. بعدها يعود /up إلى 200 دائماً، وتتوقف نداءات ميتا المجدولة. تنبيه أخطاء الاعتماد عند الإرسال يبقى، فهو من E06.

## عميل باسم مستخدم بلا رقم (مرة واحدة، على مراحل)

حين يفعّل عميل اسم مستخدم في واتساب ولم نتواصل معه خلال 30 يوماً، ترسل ميتا رسالته بلا رقم، ومعها معرّف خاص بنشاطنا (BSUID). كانت هذه الرسائل تُسقط. الآن تُحفظ في محادثة تُعرف بالمعرّف، وتظهر برقاقة «📵 رقم غير ظاهر».

1. **قبل النشر:** نسخة احتياطية: `backup:run --reason=manual --label=pre-e11a`. الهجرة `2026_10_14_000009` تعيد بناء wa_conversations لتقبل رقماً فارغاً، وتحفظ الفهارس والصفوف، وتستغرق ثوانٍ.
2. **بعد النشر:** يعمل الوضع `store` افتراضياً. تأكد بـ `docker exec -u www-data nuskjo-app php artisan whatsapp:identity-mode`. في هذا الوضع:
   - تُحفظ رسالة العميل بلا رقم، وتصير المحادثة «تدخّل»، ويُنبَّه المدير.
   - لا يُرسل إليه أحد بعد.
3. **قبل `staff`:** جرّب على رقم الاختبار في تطبيق ميتا التجريبي:
   - رسالة نصية بالحقل `recipient` إلى معرّف من أداة Test (App Dashboard › WhatsApp › Configuration › messages › Test).
   - احفظ حمولات السيناريوهات (بلا اسم مستخدم، باسم مستخدم بلا رقم، باسم مستخدم مع رقم) لتحل محل tests/Fixtures/whatsapp/username_*.json.
   ثم شغّل `whatsapp:identity-mode staff`. يرد الموظفون بالمعرّف، والبوت لا يرد.
4. **`full`** (بعد أسبوع هادئ): يرد البوت أيضاً. لا يكشف أي بيانات مالية بلا رقم، ويطلب من العميل كتابة رقمه إن سأل عن تسعير أو حجز.
- **Contact book:** أبقه مفعّلاً في Meta Business Suite › Business settings › Business info. تعطيله يحذف ما خزّنته ميتا من أرقام عملائنا.
- **التراجع:** `whatsapp:identity-mode store`. الرقم يبقى قابلاً للفراغ، ولا عودة عن الهجرة إلا بالاستعادة.

### الدفعة الثانية: الأنواع الواردة وطلب الرقم والربط اليدوي

الهجرة `2026_10_14_000012` إضافية (أعمدة الاقتباس والوسائط والإحالة ونص البحث ورقمنا المرسِل ورمز الخطأ وحالة الربط والدمج) وتمنح المدير `whatsapp.link_client`.

1. **قبل النشر:** نسخة `backup:run --reason=manual --label=pre-e11`، ثم احفظ المخطط:
   `docker exec -u www-data nuskjo-app php artisan whatsapp:verify-schema` (يحفظ JSON في `storage/app/reports` ويعيد 1 عند أي نقص؛ أعداد وأسماء فهارس فقط).
2. **النشر** ثم `whatsapp:verify-schema` مرة ثانية: عدد الصفوف وmax(id) كما هي، ولا فهرس ناقص، وintegrity_check = ok.
3. **التعبئة:** `whatsapp:backfill-identity --dry-run` (لا يكتب شيئاً)، ثم بلا `--dry-run`. يملأ المعرّف حيث جاء مع الرقم في حمولة واحدة، ولقب واتساب، والاقتباس والوسائط والإحالة ونص البحث. يمكن إعادة تشغيله بأمان.
4. **تقرير الروابط:** `storage/app/reports/wa-link-review-<التاريخ>.csv` (رقم المحادثة وكود العميل والسبب، بلا أرقام): روابط آلية قديمة يخالفها المطابق الجديد. لا يُفك شيء آلياً؛ راجعها من الصندوق بزر «🔗 تغيير الربط» أو «فك الربط».

سجل واحد لأدوات البوت والمساعد الإداري، وكل استدعاء يمر بفحص الاسم والإذن ثم التحقق ثم التنفيذ بنطاق المحادثة. ما يتغيّر عند النشر بلا علم:

- **إشعارات الجهاز للواتساب** صارت بعنوان ثابت وجسم «افتح النظام للتفاصيل» وتفتح المحادثة نفسها، والجرس بلا رقم هاتف ولا تفاصيل طلب (docs/security/DATA-MINIMIZATION.md). أخبر الموظفين.
- **رد الموظف** الذي يحوي ما يشبه رقم بطاقة أو جواز أو هوية يطلب تأكيداً قبل الإرسال، والتأكيد يُسجَّل في التدقيق.
- **بوابة المحتوى الصادر** تفحص كل رسالة آلية قبل ميتا (أرقام البطاقات والحسابات والجوازات، والتكلفة والربح، والبيانات الخام، وأسماء الأدوات) وتسجّل ما تجده. قبل الفرض: ضع حسابات الشركة المسموح ذكرها في `WA_POLICY_ALLOW_IBANS` (بلا مسافات، مفصولة بفواصل)، وراجع `php artisan whatsapp:policy-report --days=1` يومياً.

الأعلام (من إعدادات الواتساب، أو `WA_FEATURE_<KEY>` في البيئة للطوارئ؛ كلها مطفأة):
1. `tool_validation_enforce`: رفض مدخلات الأدوات غير الصالحة. قبله تُسجَّل في سجل الواتساب (`tool.validation`) وتُقصّ.
2. `admin_rbac_enforce`: لا ينفّذ رقم الإدارة إلا ما يملكه المستخدم المرتبط به بدوره، والرقم بلا مستخدم للقراءة فقط. قبله يُسجَّل ما كان سيُرفض في سجل إجراءات أرقام الإدارة بملخص يبدأ `denied_would_be`، وتعرض صفحة أرقام الإدارة التحذيرات. اربط كل رقم بمستخدمه وراجع التحذيرات قبل التفعيل.
3. `outbound_policy_enforce`: الرسالة الآلية التي تحوي ما سبق تُحجب ولا تصل العميل، وتظهر المحادثة «🛡️ حُجبت رسالة آلية» لموظف. خطأ داخل الفحص يحجب الرسالة الآلية ويمرّر رسالة الموظف.
4. `admin_readonly`: طوارئ، يوقف كل تعديل من أرقام الإدارة فوراً (`WA_FEATURE_ADMIN_READONLY=true` ثم `up -d`).
- **المراقبة أسبوعاً بعد النشر**، ثم الفرض يوماً بعد يوم: `tool_validation_enforce` ثم `admin_rbac_enforce` ثم `outbound_policy_enforce`.
- **التراجع:** إطفاء العلم فوراً، أو `git revert` ثم النشر. العمود الجديد إضافي.

- **نافذة تأكيد موحّدة** بدل نوافذ المتصفح قبل اعتماد ورفض وحذف الفواتير وسندات القبض والصرف والمسيّرات والسلف والقيود والسنوات المالية والحسابات، وسبب الرفض في حقل داخلها. اعتماد سندي القبض والصرف وحذفهما كانا بنقرة واحدة وصارا بتأكيد. التركيز يبدأ على «إلغاء» فلا يعتمد Enter خطأً، وEscape لا يضيّع تعديلات غير محفوظة في نوافذ قاعدة المعرفة وأرقام الإدارة. التأكيد حماية من الخطأ في الواجهة فقط؛ الصلاحية والاعتماد في الخادم كما هما.
- أزرار الأيقونات (🖨️ ✅ ❌ 🗑️) وزر الوضع الليلي صارت مسمّاة لقارئ الشاشة.
- مسار القائمة `/api/whatsapp/conversations` يقبل `cursor` اختيارياً ويعيد `has_more` و`next_cursor`؛ الطلب بلا cursor كما كان. لا هجرة.

التفعيل:
1. **شرط سابق:** نشر E15 (نصوص إشعارات الجهاز العامة)، لأن الجوال سيصير أكثر استعمالاً.
2. **للمدير وحده أولاً** بإضافة `?v2=1` إلى رابط الصندوق (معاينة في الواجهة، لا تتجاوز الصلاحيات)، أسبوعاً، مع جولة على iPhone (التطبيق المثبّت) وأندرويد Chrome: قائمة ← محادثة ← زر «→ المحادثات» ← رجوع الجهاز، ورابط إشعار يفتح المحادثة مباشرة، والإرسال بالزر (Enter على اللمس سطر جديد).
3. **جولة الجوال تكررها** بعد أي إصلاح خلال الأسبوع، قبل التفعيل للجميع.
4. **للجميع:** تفعيل العلم. أي إصلاح على الصندوق بعدها في المكوّنات الجديدة فقط.
5. **بعد أسبوعين بلا بلاغات:** نشر لاحق يحذف `InboxLegacy.vue` والعلم.
- **التراجع:** إطفاء العلم يعيد الصندوق القديم فوراً بلا نشر. نافذة التأكيد والخطوط بلا علم: `git revert` ثم النشر.

## لا عميل ضائع والردود الجاهزة (E17، على مراحل)

حالة متابعة داخلية للصندوق (لا شيء منها يصل العميل أو ميتا)، وتشخيص الردود العالقة، ومنع تكرار طلبات التسعير، وردود جاهزة يملأ الخادم متغيراتها. ما يعمل عند النشر بلا علم:
- الهجرة `2026_10_14_000017` إضافية: أعمدة الإغلاق والتأجيل و«غير مقروء» الداخلي، وجدولا التثبيت والردود الجاهزة، ومفتاح منع التكرار على طلبات التسعير، وصلاحية «إدارة الردود الجاهزة» للمدير.
- أي رسالة واردة تعيد فتح المحادثة المغلقة وتمسح تأجيلها.
- الرد الذي يحوي متغيراً لم يُملأ (`{{name}}` مثلاً) يُرفض قبل الإرسال.
- مجدولان جديدان: `whatsapp:snooze-wake` كل 5 دقائق، و`whatsapp:stuck-replies --notify` كل 10 دقائق (تنبيه للإدارة مرة في الساعة إن بقي عميل بلا رد آلي 15 دقيقة). للقراءة يدوياً: `php artisan whatsapp:stuck-replies` (معرّفات ودقائق انتظار فقط).
- صفحة «⚡ الردود الجاهزة» لمن يملك الصلاحية، تعمل قبل العلم لإعداد النصوص. النص الذي يذكر بيانات الدفع يُحفظ موقوفاً حتى يعتمده المدير، والسعر الثابت وطلب صور الجوازات عبر واتساب مرفوضان.

الأعلام (من إعدادات الواتساب، كلها مطفأة)، بالترتيب:
1. `quote_dedupe` أولاً: المكرر يعيد رقم الطلب نفسه بلا إشعار ثانٍ. راقب 48 ساعة في استهلاك البوت ما يبدأ بـ `dup:`.
2. `inbox_followup`، بلقطات جوال وسطح مكتب بعد التفعيل مباشرة: الإغلاق والتأجيل (حتى قبل إغلاق نافذة الرد بربع ساعة) والتثبيت (5 لكل موظف) و«غير مقروء»، والبطاقات أعلى الصندوق، وتبويبات المغلقة والمؤجلة والمثبّتة. يعمل على الصندوق الجديد (`inbox_v2`). المحادثة التي تحتاج تدخّلاً لا تُخفى مغلقة أو مؤجلة.
3. `quick_replies` بعد أن يكتب المالك النصوص الأولى ويعتمد نص الدفع: زر ⚡ و«/» في المنشئ.
4. `reprocess_button` بعد تشغيل `whatsapp:stuck-replies` يدوياً يومين: زر «🔁 إعادة معالجة» للمدير وللمحادثة العالقة وحدها، بحد 3 في 10 دقائق، ولا يحرّر قفلاً أحدث من مهلة الوظيفة، وكل إعادة في سجل التدقيق.
- **التراجع:** إطفاء العلم فوراً. مع إطفاء `inbox_followup` تعود المغلقة ظاهرة كما كانت. الأعمدة والجداول إضافية؛ `git revert` ثم النشر للضرورة.

## تصنيف أخطاء ميتا وإثبات سر التطبيق (E18، على مراحل)

لكل رفض من ميتا معنى واحد في كل النظام: رمز داخلي، وفئة، ورسالة عربية للموظف، وإجراء مقترح، وسياسة إعادة (تنفذها E19). الجدول الوحيد `App\Services\WhatsApp\MetaErrorCatalog`، وكل نداء Graph عبر `Graph\GraphClient` وحده. ما يعمل عند النشر بلا علم:
- الهجرة `2026_10_14_000018` إضافية: عمود فئة الخطأ على الرسائل، وفهرس (الاتجاه، الحالة، الوقت)، و`wa_last_error` على الإعدادات، وتعبئة متساوية الأثر من الرموز المحفوظة. خذ نسخة قبلها، وقارن عدد الصفوف وأكبر معرّف بعدها.
- **وضع الظل:** كل فشل يُصنَّف ويُكتب (الرمز الداخلي والفئة وسطر `wa.send_failed` أو `wa.delivery_failed` بالمعرّفات وحدها)، و`wa_last_error` وعدّادات الفئات تتحدّث، لكن النص المعروض والتنبيه والإيقاف كما كانت.
- بطاقة «آخر خطأ من ميتا» في الإعدادات › صحة النظام والقناة: الرمز والوصف والإجراء وعدد 24 ساعة وfbtrace_id للدعم، وزر «تمّ الحل» (يصفّر السطر ولا يرفع إيقاف الإرسال)، وعدّادات اليوم لكل فئة، ونسبة إثبات سر التطبيق خلال 7 أيام.
- `whatsapp:doctor` يعرض جدول الإثبات لآخر 7 أيام، وفئات اليوم، والرموز المجهولة. العدّادات في مخزن file (`WA_GRAPH_COUNTER_STORE`).

العلم `meta_error_v2` (مطفأ):
1. ثلاثة أيام ظل: راجع يومياً سطور `wa.send_failed` في `storage/logs/whatsapp-*.log` وبطاقة الفئات، وقارن `error_code` الجديد بالنص القديم في الصندوق.
2. فعّل العلم وراقب 48 ساعة. بعده يرى الموظف تحت «فشل» سبباً عربياً ملوّناً وزر «ⓘ ماذا أفعل؟»، والمنشئ يعرض الإجراء بعد السبب، ومهلة ميتا ترد 503 «قد تكون وصلت» وتترك صفاً «غير مؤكد»، وفشل الاتصال يترك صفاً فاشلاً ظاهراً لكل مصدر. المدير يرى شريطاً أحمر في الصندوق عند خطأ اعتماد أو تقييد على القناة، وغيره سطراً عاماً. التنبيه مرة في الساعة لكل رمز، والإيقاف الآلي على 368 وحده (`WA_AUTOSUSPEND_CODES`)، ورسالة الموظف التي لم تصل لسبب عند العميل تُبلغ مرسلها مرة واحدة.

إثبات سر التطبيق (`WA_APPSECRET_PROOF`):
1. تأكد أن سر التطبيق المحفوظ هو سر التطبيق المرتبط بالرمز (App Dashboard › Settings › Basic).
2. `WA_APPSECRET_PROOF=true` في `.env.production` لنسك ثم `docker compose up -d` (بلا بناء). مباشرة بعده: رسالة نصية وبطاقة عرض ورسالة صوتية، و`whatsapp:doctor` يُظهر رفض إثبات = 0. عند أي رفض: `WA_APPSECRET_PROOF=false` فوراً ثم `up -d`.
3. سبعة أيام متتالية على الإنتاج: النداءات = بإثبات، وصفر رفض (`whatsapp:doctor` أو سطر البطاقة «جاهز لتفعيل Require App Secret»). تُسجَّل النتيجة في CHANGELOG، وهي شرط بدء E26. لا يُفعَّل «Require App Secret» في لوحة ميتا قبلها.
- **التراجع:** `meta_error_v2` إلى off من الإعدادات فوراً. `WA_APPSECRET_PROOF=false` ثم `docker compose up -d` بلا بناء. الأعمدة إضافية بلا ضرر.

## دفتر الإرسال ومنع التكرار (E19، على مراحل)

كل رسالة صادرة تُكتب صفاً «قيد الإرسال» قبل خروجها إلى ميتا، ثم يُحسم الصف نفسه: أُرسلت، أو فشلت (ويُحرَّر مفتاحها لإعادة مشروعة)، أو «غير مؤكد» (ربما وصلت، والمفتاح محجوز فلا يكررها أحد). لكل إرسال آلي مفتاح حتمي، ولكل رسالة موظف مفتاح من المنشئ (Idempotency-Key)، فنقرتان أو إعادة وظيفة لا تُخرجان رسالتين للعميل. ما يعمل عند النشر بلا علم:
- الهجرة `2026_10_14_000019` إضافية: عدد المحاولات، وأعلى وارد غطّاه الرد، ووقت قبول ميتا، وفهرس للمنظّف. وحالة «غير مؤكد» القديمة (`unconfirmed`) صارت `unknown` بالمعنى نفسه.
- المنشئ يرسل مفتاح المسودة مع كل رسالة. بلا العلم لا أثر له.

العلم `send_ledger` (مطفأ):
1. فعّله في ساعة هادئة. جرّب من الصندوق: رسالة عادية، ونقرتين سريعتين على «إرسال» (رسالة واحدة عند العميل)، وسعراً مرتين من طلبات التسعير خلال دقائق (الثانية «أُرسل هذا السعر نفسه قبل قليل»)، و«أعد الإرسال للعميل» الصريح (يرسل).
2. راقب 72 ساعة: لا يبقى صف «⏳ قيد الإرسال» أكثر من 15 دقيقة (المنظّف `whatsapp:reap-pending` كل 10 دقائق يحوّله «⚠️ غير مؤكد» وينبّه)، وأعداد «إرسال غير مؤكد» و«فشل إرسال» في صفحة التحليلات، وسطور `wa.send.*` في سجل الواتساب.
3. «غير مؤكد» يُحسم آلياً حين تصل حالة ميتا (رقم الصف في biz_opaque_callback_data). وما بقي بعد المنظّف يظهر بزر «✍️ انسخ إلى خانة الكتابة»: لا إعادة آلية أبداً، والموظف يقرر بعد تأكيد صريح.

العلم `send_retry` بعد أسبوع نظيف من `send_ledger`: إعادة محدودة لرموز ميتا العابرة والخنق ولتعذّر الاتصال قبل الإرسال وحدها، بانتظار ثانية ثم 4 ثوانٍ (أقل من 10 مجموعاً)، مع إعادة فحص النافذة والإيقاف والنطاق قبل كل محاولة. لا إعادة بعد مهلة الطلب ولا بعد خطأ 5xx بلا رد مفهوم. راقب سطور `wa.send.retry`.
- **التراجع:** `send_retry` ثم `send_ledger` إلى off من الإعدادات فوراً. الصفوف «قيد الإرسال» و«غير مؤكد» تبقى ظاهرة، والمنظّف لا يعمل والعلم مطفأ. الأعمدة إضافية.

## استقبال الويبهوك المتين (E20، على مراحل)

العقد كاملاً في `docs/whatsapp-webhook-contract.md`. ما يعمل عند النشر بلا علم:
- **الحجم أولاً:** جسم فوق 4MB يرد 413 قبل حساب التوقيع.
- **التوقيع الفاشل وحده يُعدّ:** عدّاد في الساعة وآخر في اليوم، وتنبيه عند 20 في الساعة. لا 429 أبداً.
- **عزل العناصر:** كل change ورسالة وحالة معزولة، فعنصر فاشل لا يُسقط ما بعده في الحمولة.
- **التكرار:** تعارض wamid تكرار ناجح. والحالة المكررة لا تُلحق مرتين. وإعادة حدث حساب سلبي لا تكرر الإشعار ولا الإيقاف.
- **الحقول خارج المعالجة:** تُسجَّل باسمها وعددها فقط، ومنها calls. وأحداث التعايش (smb_message_echoes) تنبّه فوراً ولا تصل للبوت.
- **الهجرة `2026_10_14_000020`:** جدول جديد `wa_webhook_events` وعمود `wa_waba_id_source`. إضافية بلا إعادة بناء.
- **nginx:** كتلة خاصة بالمسار بحد 4m ومهلة 60 ثانية، و`keepalive_timeout 100s`. الحد العام 50M باقٍ حتى تحسم E32 حاجة الرفع (A16). جُرّبت بحاويتَي nginx وphp-fpm: 413 فوق 4MB حتى بلا Content-Length، وسطر السجل بلا query.
- **ما يُراقب بعد النشر:** `whatsapp:doctor` يعرض قسم «الويبهوك»: حد nginx المنشور، والمسار خارج الجلسة، والأعداد.

العلم `inbound_event_log` (مطفأ)، وهو الحفظ قبل الإقرار والإعادة:
1. انشر `/privacy` و`/data-deletion` أولاً. السطر الجديد «إشعارات واتساب التي تعذّرت معالجتها: 72 ساعة كحد أقصى» يُنشر مع الكود.
2. فعّله في ساعة هادئة، وأرسل رسالة من هاتف الاختبار. في بطاقة «📥 استقبال الويبهوك» تظهر «عولج 1»، وأقدم جسم محفوظ «—».
3. راقب 72 ساعة:
   - المعالَج مقابل «ينتظر الإعادة» و«تعذّر».
   - سطور «database is locked» في سجل الواتساب.
   - تنبيهات فشل التسليم في App Dashboard: 503 يجب أن تبقى نادرة، وهي فقط لفشل الحفظ مع `webhook_5xx`.
   - إن ظهر ضغط كتابة: `WA_WEBHOOK_LOG_MODE=failures`، فلا يُحفظ الجسم إلا عند الخطأ.
4. `whatsapp:replay-webhooks` كل دقيقة يعيد الفاشل (3 محاولات ثم «تعذّر» مع تنبيه). `whatsapp:webhook-events-prune` كل ساعة يمحو الأجسام بعد 72 ساعة، والأثر الوصفي بعد 14 يوماً.
   - لإعادة صف بعينه بعد إصلاح علة: `whatsapp:replay-webhooks --id=… --force`، ويُدقَّق.

العلم `webhook_fence_enforce` (مطفأ = تسجيل):
1. قارن «المكتشف من ميتا» في «ربط قناة ميتا» بمعرّف حساب الأعمال في WhatsApp Manager.
2. اضبط المعرّف: `WA_WABA_ID` في البيئة، أو من الحقل نفسه بتأكيد. التحذير الأحمر يظهر إن اختلفا.
3. أسبوع بوضع التسجيل. في البطاقة يجب أن يبقى عمود «كان سيُرفض» صفراً للحمولات الحقيقية.
4. فعّل الفرض. المرفوض يُعدّ ولا يُخزَّن محتواه، مع تنبيه عند أول رفض في اليوم.
- **التراجع:** العلمان إلى off وقت التشغيل. الجدول لا يؤذي إن بقي، و`whatsapp:webhook-events-prune` يمحو أي جسم متبقٍ. والمسار في `routes/webhooks.php` منذ E07، فلا يُنقل.

## حالات التسليم والناقل الداخلي (E21، على مراحل)

ما يعمل عند النشر بلا علم:
- **الهجرة `2026_10_14_000021`** إضافية: وقت ميتا للحالة على الرسائل الصادرة (`status_at`)، ومصدر إيقاف التسويق في `wa_optouts` (`source`). لا تمس صفاً قائماً، وتُترك عند التراجع.
- **ستة أحداث داخلية** تُطلق بعد اعتماد المعاملة وعند تغيّر فعلي وحده، بمعرّفات ورموز فقط. لا أثر لها والأعلام مطفأة. العقد في `docs/whatsapp/events.md`.
- **زر البوت في المحادثة** يرسل القيمة المطلوبة، فنقرتان لا تعكسان النتيجة. تبويب قديم بلا قيمة يقلبها ويترك سطر `wa.toggle_bot.legacy`.
- **مصدر إيقاف التسويق** يُكتب مع كل إيقاف: كلمة (`text`) أو زر (`button`).
- **بعد النشر:** `docker exec nuskjo-app php artisan event:list | grep WhatsApp` يُظهر المستمعين الثلاثة.

العلم `delivery_status_v2` (مطفأ):
1. قبله تحقق من إصدار SQLite في الحاوية، والمطلوب 3.31 أو أحدث: `docker exec nuskjo-app php -r "echo SQLite3::version()['versionString'], PHP_EOL;"`.
2. فعّله في ساعة هادئة. أرسل رسالة من هاتف المدير ثم رد من الصندوق: تظهر ✓ ثم ✓✓ ثم ✓✓ على شارة زرقاء خلال دورتي استطلاع.
3. راقب 48 ساعة في سجل الواتساب:
   - `wa.status.history_failed` يجب أن يبقى صفراً.
   - `wa.status.orphan` نادر، ويتبعه `wa.status.orphan_applied`.
   - `wa.status.unknown_value` يعني قيمة حالة جديدة من ميتا لا نكتبها.
4. الحالة بعده لا تتراجع: «سُلّمت» المتأخرة لا تنزل فوق «قُرئت»، و«فشلت» المتأخرة تبقى تلميح «فشل على أحد الأجهزة».

العلم `wa_event_bus` (مطفأ)، بعد يومين نظيفين من `delivery_status_v2`:

## إشعار القراءة ومؤشر الكتابة (E35، على مراحل)

العلامتان الزرقاوان و«يكتب…» طلب واحد عند ميتا، فالمؤشر يُظهر القراءة حتماً. يحكمهما إعداد واحد في «ربط قناة ميتا»: «لا شيء» (الافتراضي)، أو «عند الرد»، أو «عند الرد والفتح». وفوقه العلم `read_receipts` (مطفأ = لا يصل ميتا شيء). الطلب ليس رسالة: لا صف في الخيط ولا دفتر ولا نافذة 24 ساعة. الإيقاف الطارئ يمنعه، وفشله لا يمنع أي رد ولا يغيّر صحة القناة.
- الهجرة `2026_10_14_000035` إضافية: عمود الوضع (off) وعمود «آخر وارد أُبلغ بقراءته» لكل محادثة. لا يتغير شيء للعميل بعدها.
- `whatsapp:doctor` يعرض الوضع الفعلي والمضبوط، وإخفاقات اليوم، وآخر رمز خطأ.

التفعيل:
1. نسخة `backup:run --reason=manual --label=pre-E35`، ثم النشر والهجرة.
2. في ساعة هادئة: اختر «عند الرد» من الإعدادات (يطلب تأكيداً)، ثم فعّل العلم `read_receipts` من لوحة الأعلام.
3. من هاتف الاختبار على نسك: رسالة للبوت يظهر بعدها «يكتب…» خلال ثانيتين ثم الرد. ورسالة يرد عليها موظف من الصندوق فتظهر العلامتان عند الرد. فتح المحادثة في الصندوق لا يُظهر شيئاً. وفي الخيط 👁 على ما أُبلغ العميل بقراءته.
4. راقب 48 ساعة: إخفاقات اليوم في `whatsapp:doctor`، وسطور `wa.read_receipt_failed` في سجل الواتساب، وأي 130429. وراجع تقرير الفوترة في WhatsApp Manager أسبوعاً: الطلب ليس رسالة محاسَبة.
5. إن رفض إصدار Graph المؤشر (كل طلبات «يكتب…» تفشل): `WA_TYPING_INDICATOR=false` ثم `docker compose up -d`. تبقى العلامتان عند رد الموظف وحدهما.
6. «عند الرد والفتح» بطلب صريح من المالك فقط. يرى الموكَّل في الخيط سطراً: «فتحك لهذه المحادثة يُظهر للعميل أنك قرأت رسائله».
- **التراجع:** «لا شيء» أو العلم مطفأ من الإعدادات فوراً، أو `WA_FEATURE_READ_RECEIPTS=false` ثم `docker compose up -d`. العمودان إضافيان بلا ضرر للكود القديم.

## الردود الحتمية والمكوّنات الرسمية (E37، على مراحل)

القاعدة نص ثابت يعتمده المالك لسؤال متكرر (الموقع، مواعيد الدوام، طريقة التواصل). ترد بعد كل بوابات البوت وقبل النموذج، وتبقى تعمل أثناء عطل مزوّده. تمر عبر القناة ودفتر الإرسال كأي رد آلي. التفصيل في `docs/whatsapp/auto-rules.md`.
- الهجرة `2026_10_14_000037` إضافية: جدول `wa_auto_rules`، وعمودان في الإعدادات (`auto_rules_mode` بقيمة «ظل»، و`conversational_automation`)، وصلاحية «إدارة الردود الحتمية» للمدير. لا قواعد بعدها، ولا يتغير شيء للعميل.
- مجدول جديد `whatsapp:inbound-silence` كل 15 دقيقة، لا يفعل شيئاً والعلم مطفأ.

التفعيل:
1. نسخة `backup:run --reason=manual --label=pre-E37`، ثم النشر والهجرة.
2. يعتمد المالك نصوص القواعد الأولى كتابةً، بلا أسعار ولا بيانات دفع. أدخلها من «🧩 الردود الحتمية» (تُحفظ موقوفة)، ثم «جرّب نصاً» و«محاكاة على السجل» لكل منها. ضيّق القاعدة الموسومة «واسعة جداً» قبل تفعيلها.
3. في ساعة هادئة: فعّل القواعد من الصفحة، ثم العلم `auto_rules` والوضع «ظل». أسبوع ظل (7 أيام): قارن عدّاد الظل لكل قاعدة بالمحادثات الفعلية، هل كانت ستجيب صواباً؟ لا يصل العميل شيء منها في الظل.
4. «▶️ التحويل إلى الإرسال الفعلي» من الصفحة، ويطلب تأكيداً. من هاتف الاختبار على نسك:
   - «الموقع» يأتي برد القاعدة، وفي الخيط شارة «⚡ قاعدة».
   - السؤال نفسه ثانية خلال التهدئة يجيبه النموذج.
   - السؤال المركّب أو الطويل يجيبه النموذج.
5. راقب 72 ساعة:
   - عدد مرات المطابقة لكل قاعدة في الصفحة.
   - سطور `auto_rule_invalid` و`auto_rule_text_rejected` و`auto_rule_variable_empty` في سجل الواتساب.
   - ملاحظات الموظفين على الردود.

المكوّنات الرسمية (العلم `conversational_components`، بعد أسبوع الظل):
1. سمِّ كل أمر باسم قاعدة `exact` تجيبه («الموقع» للقاعدة «/الموقع»)، ثم «مزامنة مع واتساب».
2. «قراءة الحالي من واتساب» يجب أن تعرض «مطابق».
3. من هاتف الاختبار: افتح المحادثة لترى أسئلة البداية، واكتب «/» لترى الأوامر. قد يتأخر ظهورها عند واتساب.

صمت الوارد (العلم `inbound_silence_alert`):
1. إن اختلف الدوام عن «السبت إلى الخميس 09:00-21:00» فاضبط `business_hours` في `config/ops.php`، والعتبة بـ `OPS_INBOUND_SILENCE_MINUTES` (180 دقيقة افتراضياً).
2. فعّل العلم. سطر «آخر حدث من ميتا» في بطاقة «🩺 صحة النظام والقناة» يجب أن يتحرك مع كل رسالة.
3. `php artisan whatsapp:inbound-silence` يطبع حكم الفحص وآخر حدث.

- **التراجع:**
  - القواعد: «⏸️ العودة إلى الظل»، أو العلم `auto_rules` مطفأ فوراً، أو `WA_FEATURE_AUTO_RULES=false` ثم `docker compose up -d`. القواعد تبقى محفوظة ولا تعمل.
  - المكوّنات: «مسح من واتساب»، ثم العلم مطفأ.
  - صمت الوارد: العلم مطفأ.
  - الجدول والأعمدة إضافية، فلا تضر الكود القديم.

## الملفات من الصندوق وفاتورة PDF (E32، على مراحل)

كل رسالة صادرة تمر بمغلف واحد (`WhatsAppChannel::send`): النافذة والإيقاف والنطاق وبوابة المحتوى ودفتر الإرسال ومفتاح منع التكرار وتصنيف أخطاء ميتا كما للنص. الموظف يرسل من الصندوق صورة JPG/PNG أو PDF أو فيديو MP4 بحوار تأكيد إلزامي (المستلم بالاسم وآخر 4 أرقام، ونوع الوثيقة، وتأكيد ثانٍ للتأشيرة)، والفاتورة المعتمدة تصير PDF بلا تكلفة للتنزيل وللإرسال على واتساب. **الرفع إلى ميتا مؤجل دائماً:** الطلب يفحص الملف ويحفظه ويضعه في الطابور `wa-media-out` ويرد 202، والوظيفة ترفعه ثم ترسله. ما يتغيّر عند النشر بلا علم:
- **الهجرة `2026_10_14_000032`** إضافية: عمود `media_remote_deleted_at` على الرسائل (بحارس وجود، و`down` بلا حذف).
- **nginx:** كتلة خاصة بمسار `send-file` بحد 20m ومهلة 60 ثانية. الحد العام 50M وكتلة الويبهوك (4m) و`keepalive_timeout 100s` كما هي. تتطلب إعادة بناء الصورة.
- **العامل `laravel-media`** صار `--queue=wa-media-out,wa-media`: ملفات الموظف قبل أرشفة الوارد. بعد النشر `supervisorctl status` يُظهره RUNNING. الوظيفة 120 ثانية بمحاولة واحدة، والملف الأقدم من 10 دقائق في الطابور لا يُرسل (`MEDIA_QUEUE_STALE`).
- **المجدولات:** `whatsapp:outbound-media-cleanup` كل ساعة (لا يعمل إلا بعلمه). `whatsapp:media-sweep` يكنس أيضاً ملفات `outbound/` اليتيمة ونسخ الفواتير المؤقتة بعد 7 أيام. `whatsapp:reap-pending` يجعل الملف الذي لم تبدأ محاولته «فشل» لا «غير مؤكد».
- **حد الإرسال:** 10 ملفات في الدقيقة و60 في الساعة لكل موظف (ويشمل الفاتورة). وفحص `/up` لا يعدّ طابور `wa-media-out`.
- **التدقيق:** «إرسال ملف لعميل على واتساب» (التأشيرة بدرجة تحذير) و«إرسال فاتورة PDF على واتساب».
- **قبل النشر:** نسخة `backup:run --reason=manual --label=pre-e32`، ومساحة القرص (`df -h`): كل ملف مرسل تبقى نسخته على `wa_media` تحت `outbound/` وتُقلَّم مع الأرشيف.

الأعلام (من إعدادات الواتساب، أو `WA_FEATURE_<KEY>` للطوارئ؛ كلها مطفأة)، بالترتيب:
1. `staff_file_send` في ساعة هادئة. جرّب على نسك مع هاتف الاختبار: PDF صغير، وصورة JPG، وصورة HEIC من iPhone (تتحول JPEG في المتصفح)، ومقطع MP4 قصير. المتوقع: فقاعة «⏳ في الطابور» ثم صف «قيد الإرسال» ثم «أُرسلت»، وحوار التأكيد يسمّي العميل وآخر 4 أرقام. راقب 72 ساعة: سطور `wa.media.queued` و`wa.media.uploaded` و`wa.media.upload_failed` في سجل الواتساب، والصفوف الفاشلة برموز `MEDIA_*`، وطول الطابور (`jobs` حيث `queue='wa-media-out'`).
2. `invoice_whatsapp_send` بعد أسبوع نظيف: زر «⬇️ PDF» (يراه المدير قبل العلم للمعاينة) و«📤 واتساب» للفاتورة المعتمدة وحدها. قارن PDF بصفحة الطباعة: لا تكلفة ولا ربح ولا وكيل. أرسل فاتورة لمحادثة الاختبار، ويظهر «إرسال فاتورة PDF على واتساب» في سجل التدقيق.
3. `offer_card_by_media_id`: بطاقة العرض تُرفع وتُرسل بالمعرّف بدل الرابط العام، ويُعاد استعمال المعرّف 25 يوماً. جرّب بطاقة عرض من البوت.
4. `outbound_media_remote_delete` بقرار المالك: يحذف الملف المرسل من خوادم ميتا بعد قراءته (الأنواع والحالات من البيئة، المستندات المقروءة افتراضياً). نسختنا باقية، والفقاعة تقول «حُذف من خوادم واتساب بعد القراءة»، والعميل لا يعيد تنزيله إن حذفه من هاتفه. جرّب `php artisan whatsapp:outbound-media-cleanup --dry-run` أولاً.

قرارات المالك (الافتراضي بين قوسين): حد المستند `WA_OUTBOUND_MAX_DOCUMENT_MB` (16، وحتى 19 بلا تعديل nginx)؛ ملفات Office `WA_OUTBOUND_OFFICE_DOCS` (مطفأة، والصيغ القديمة مرفوضة دائماً)؛ الفيديو `WA_OUTBOUND_VIDEO` (مفعّل)؛ ورق الشركة في الفاتورة `INVOICE_PDF_LETTERHEAD` (مفعّل) والرقم الضريبي `INVOICE_PDF_SHOW_TAX` (مطفأ)؛ الحالات القابلة للإرسال `INVOICE_WHATSAPP_STATUSES` (approved)؛ الحذف من ميتا `WA_OUTBOUND_REMOTE_DELETE_TYPES`/`_STATUSES` (document/read).
- **التراجع:** العلم إلى off من الإعدادات فوراً يخفي الزر ويرفض المسار. ما في الطابور لحظتها يُرسل لأن موظفاً أكّده، إلا إن أُوقف الإرسال كله (الوظيفة تعيد فحص الإيقاف والنافذة). `git revert` ثم النشر للضرورة؛ العمود إضافي، وإعادة العامل إلى `--queue=wa-media` تترك أي ملف عالق ليحسمه المنظّف «فشل».

## التحقق بخطوتين للموظفين (E27، على مراحل)

كلمة المرور وحدها لا تكفي إن سُرقت: رمز من تطبيق مصادقة على هاتف الموظف عند كل دخول جديد، وتأكيد هوية قبل الأفعال الحساسة. كل شيء على خادمنا: الرمز بحسب RFC 6238 وصورة QR تُرسم هنا، بلا حزمة جديدة ولا خدمة خارجية ولا رسائل واتساب. ما يعمل عند النشر بلا علم:
- **الهجرة `2026_10_14_000027`** إضافية: أعمدة العامل الثاني وآخر نشاط وآخر عنوان دخول في `users`، و`require_mfa` لأرقام الإدارة. خذ نسخة قبلها.
- **الحضور** يقبل `ip` و`geo` وحدهما، والواجهة ترسل `geo`. التعديل اليدوي من صفحة الحضور بصلاحيته، ويُدقَّق.
- **كوكي الجلسة** صار Secure لأن `APP_URL` يبدأ بـ https. الدخول المباشر بـ http إلى المنفذ لا يعمل بعده؛ للطوارئ فقط `SESSION_SECURE_COOKIE=false`. `whatsapp:doctor` ينبّه إن غاب القيد.
- **مجدولان:** `users:sync-last-seen` كل 15 دقيقة باستعلام واحد من جدول الجلسات، و`users:idle-report` صباح الأحد. الثاني لا يرسل إلا بالعلم `idle_report`، ولا يعطّل أحداً.
- **المستخدمون:** أعمدة «2FA» و«آخر دخول» و«آخر نشاط»، وفلترا «يتطلب ولم يفعّله» و«خامل». آخر عنوان دخول لمن يملك تعديل المستخدمين وحده.

الأعلام والمتغيرات بالترتيب، كلٌّ في ساعة هادئة. الأعلام الثلاثة الأولى يبدّلها المدير وحده من الإعدادات، أو `WA_FEATURE_*` في `.env.production`:
1. **`staff_mfa`:** يظهر رابط «🔐 الأمان والتحقق بخطوتين» في إعدادات الحساب. يسجّل المدير أولاً بهاتفه الشخصي، ويحفظ الرموز العشرة خارج الهاتف، ثم يخرج ويدخل ليجرب التحدّي. يُفضَّل مديران بعامل ثانٍ.
2. **`step_up` بعد أسبوع:** الاعتماد والإعدادات والأسرار والمستخدمون والأدوار وأرقام الإدارة والإقفال المحاسبي وتصدير التدقيق تطلب تأكيد الهوية مرة كل ربع ساعة على الأكثر، ثم يُعاد الفعل تلقائياً. القائمة في `config/security.php`. الإيقاف الطارئ لا يُعاق، واستئنافه يطلبه.
3. **`MFA_ENFORCE=warn`** و`MFA_ENFORCE_FROM` بعد 14 يوماً، في `.env.production` ثم `docker compose up -d nuskjo-app`. يرى أصحاب الصلاحيات الحساسة شريطاً أصفر. أبلغهم، وتابع عمود «2FA» وفلتره.
4. **`MFA_ENFORCE=on`:** بعد التاريخ لا تُفتح لمن لم يسجّل إلا صفحة «الأمان». راقب أسبوعاً `auth.mfa_failed` و`auth.mfa_lockout` في سجل التدقيق.
5. **`admin_number_mfa`:** بعد أن يسجّل أصحاب أرقام الإدارة التي تعدّل. الرقم الذي يعدّل يحتاج حساب صاحبه، ويتوقف مساعده برسالة واحدة في اليوم حتى يفعّل صاحبه التحقق.
6. **`idle_report`**، و`PASSWORD_MIN_LENGTH=10` مع `PASSWORD_LETTERS_AND_NUMBERS=true` بقرار المالك.

فقد الموظف عامله الثاني، والقفل بعد محاولات خاطئة، ومنفذ الطوارئ `MFA_CHALLENGE`: الكتيّب RB-16 في [RUNBOOK.md](RUNBOOK.md#rb-16).
- **تدوير APP_KEY:** أبقِ المفتاح القديم في `APP_PREVIOUS_KEYS`، فأسرار التحقق مشفّرة به.

جانب ميتا، يدوي للمالك، ويُراجع كل ربع سنة: PIN التحقق بخطوتين للرقم معروف ومحفوظ خارج الخادم (أو يُغيَّر من WhatsApp Manager › Two-step verification)، و2FA لكل أعضاء Business portfolio بالقيمة Everyone، ولا موظف سابقاً في People وSystem users، ورمز System User بصلاحيتين فقط. لا رموز دخول عبر قوالب واتساب.
- **التراجع:** `MFA_ENFORCE=off` يعيد الدخول بكلمة المرور، ويبقى التحدّي لمن سجّل. `step_up` وبقية الأعلام إلى off. `STEPUP_TTL` أكبر يقلل الأسئلة. الأعمدة تبقى بلا ضرر.

## الحظر الرسمي وملف واتساب للأعمال (E31، على مراحل)

قدرتان رسميتان من Cloud API: حظر جهة اتصال وفكّه عند ميتا (Block Users API)، ومزامنة ملف واتساب للأعمال مع بيانات الشركة. ما يعمل عند النشر بلا علم:
- **الهجرة `2026_10_14_000031`** إضافية: جدول `wa_blocks` (من حظر ومتى ولماذا وحالته عند ميتا)، وعمود `blocked_at` على المحادثات بفهرس، وصلاحية «حظر جهات اتصال واتساب» (`whatsapp.block`) للمدير وحده، وثلاثة صفوف إعدادات فارغة في «بيانات الشركة»: الموقع الإلكتروني، ونبذة واتساب (139 حرفاً بلا تنسيق)، ووصفه (512). خذ نسخة قبلها (`pre-e31`)، وقارن بعدها عدد صفوف المحادثات وأكبر معرّف.
- قفل الإرسال لمحادثة محظورة، وتخطي البوت لها، وإخفاؤها من بطاقات «ينتظر موظفاً» و«نافذة تُغلق» ومن تذكير النافذة: كلها تعمل بالعمود وحده، ولا محادثة محظورة قبل تفعيل العلم.
- `/privacy` فيه سطر الحظر الرسمي، وبقاء الحظر ببصمة بلا رقم ولا سبب بعد «حذف بياناتي».
- مجدول جديد `whatsapp:blocks-check` يومياً 04:10: قراءة قائمة ميتا ومقارنتها، بلا أي تغيير عند ميتا. لا يعمل والعلم مطفأ.
- بطاقة «📇 ملف واتساب للأعمال» في إعدادات الواتساب تقرأ الملف من ميتا وتقارنه ببيانات الشركة (قراءة GET كل 10 دقائق حداً أقصى)، واسم العرض للقراءة فقط: يُغيَّر من WhatsApp Manager وحده.

العلم `wa_block` (مطفأ):
1. على نسك خلف العلم المطفأ: امنح `whatsapp.block` لمن يملك قرار الحظر (المدير يملكها). التفاصيل النصية للسبب يراها حاملها وحده.
2. فعّله في ساعة هادئة. جرّب على رقم اختبار راسلنا اليوم: «⛔ حظر» في رأس المحادثة (معطّل خارج 24 ساعة من آخر رسالة للعميل، شرط ميتا)، سبب وتفاصيل، وآخر 4 أرقام للتأكيد. يظهر الشريط الأحمر، ويُقفل المنشئ، ويتوقف البوت. ثم «فك الحظر» بسبب: البوت لا يعود تلقائياً.
3. صفحة «⛔ المحظورون»: القائم والسجل، و«مزامنة الآن» تقرأ قائمة ميتا وتعرض ما لم تجده ميتا، وما هو محظور عند ميتا بلا سجل عندنا (يُسجَّل سببه أو يُفك)، وما وصلت منه رسالة. كل إصلاح بزر وسبب.
4. راقب أسبوعاً: سطور `wa.block.*` في سجل الواتساب، وتدقيق «حظر» و«فك حظر» (خطورة تحذير)، وتنبيه `whatsapp:blocks-check` عند زيادة غير الموجود أو غير المسجّل.
- `wa_block_bsuid`: حظر من لا رقم ظاهراً له بمعرّفه، بعد تجربة رقم اختبار بلا رقم ظاهر. المعرّف الأم (.ENT.) لا يُحظر أبداً.
- `wa_block_admin_tool`: أداة «احظر» للمساعد الإداري بمعاينة ثم «تأكيد»، لصاحب رقم إدارة مربوط بمستخدم يملك `whatsapp.block`. بوت العملاء لا يملك أي أداة حظر.
- `WA_BLOCK_NOTIFY=false` يطفئ إشعار المدراء بكل حظر (بلا رقم ولا اسم).

ملف واتساب للأعمال:
1. أكمل في «إعدادات النظام › بيانات الشركة»: النبذة (حتى 139، بلا * ولا _ ولا ` ولا ~، والروابط فيها لا تُنقر)، والوصف (حتى 512)، والموقع (يبدأ بـ https://، والثاني صفحة فيسبوك). البريد والعنوان من حقولهما.
2. تحقّق أن رمز System User يحمل `whatsapp_business_management` (فحص الرمز في «صحة النظام والقناة»)، وإلا رفضت ميتا القراءة.
3. العلم `business_profile_sync`: اختر الحقول المختلفة، وراجع «قبل/بعد»، ثم «مزامنة». نوع النشاط سفر (TRAVEL) دائماً. القيم تُحسب في الخادم من بيانات الشركة وحدها، وتُقرأ بعد الكتابة للتحقق، وتُدقَّق بالقيم السابقة (للإرجاع يدوياً).
4. العلم `business_profile_photo` (اختياري): يحتاج App ID. JPEG أو PNG مربعة 192px على الأقل وحتى 5MB، أو شعار الشركة.
- **التراجع:** الأعلام إلى off من الإعدادات فوراً: تختفي الأزرار والصفحة (404)، والمحادثات المحظورة تبقى مقفلة عندنا لأن الحظر قائم عند ميتا. لفك حظر بعد إطفاء العلم: أعد تفعيله مؤقتاً وفكّه من الصفحة، أو من تطبيق واتساب نفسه ثم «مزامنة». الجدول والعمود إضافيان بلا أثر.

## رموز QR الرسمية وبطاقة الحالة ومصدر المحادثة (E38، على مراحل)

ثلاثة أشياء رسمية أو داخلية، كلٌّ بعلمه: رمز QR ورابط قصير لكل عرض عبر `message_qrdls` (المسح يفتح محادثة برسالة معبأة يرسلها العميل بنفسه، فلا مراسلة باردة)، وبطاقة حالة 9:16 تُنزَّل للنشر اليدوي، وتسجيل مصدر المحادثة لقياس الحملات. لا نشر آلي للحالة أبداً. ما يعمل عند النشر بلا علم:
- **الهجرة `2026_10_14_000038`** إضافية: جدولان جديدان (`wa_qr_links` و`wa_conversation_entries`) وثلاثة أعمدة على العروض (مسار بطاقة الحالة ووقتها، والرمز المطبوع على بطاقة A4). لا صلاحيات جديدة. خذ نسخة قبلها (`pre-e38`)، وقارن بعدها عدد العروض وأكبر معرّف.
- `/privacy` فيه سطر «نسجّل مصدر بدء المحادثة (رمز QR أو رابط أو إعلان) لقياس حملاتنا، دون مشاركته مع أي طرف».
- مجدول جديد `whatsapp:qr-sync` أسبوعياً (الأحد 04:25): مطابقة قرائية مع ميتا، بلا حذف آلي، وتنبيه فوق 1800 رمز. لا يعمل والعلم مطفأ.

العلم `entry_tracking` (مطفأ) أولاً، وهو قراءة داخلية بحتة:
1. فعّله في ساعة هادئة. أي رسالة تحمل مرجعاً مثل `[N-45/Q7]`، أو تأتي من إعلان انقر للواتساب، تسجّل صف مصدر، وتسم المحادثة بموضوع العرض (المصدر «رمز» أو «إعلان») وتوكل مختصّه بصمت، ويعرف البوت العرض المقصود من أول رسالة. في رأس المحادثة «📷 من رمز» أو «📣 من إعلان».
2. راقب يومين: سطور `wa.entry.*` في سجل الواتساب، وقسم «📍 مصادر المحادثات» في التحليلات (أعداد فقط، قياس داخلي تقريبي). لا يُحفظ ctwa_clid ولا نص الإعلان ولا روابط صوره.

العلم `wa_qr_links` (مطفأ):
1. تحقّق أن رمز System User يحمل `whatsapp_business_management` (فحص الرمز في «صحة النظام والقناة»).
2. فعّله، وأنشئ من تبويب «📤 المشاركة» في عرض واحد رمزاً بالقناة «طباعة». امسحه بهاتفين (أندرويد وiOS): المحادثة تُفتح على رقمنا الرسمي والرسالة المعبأة تحمل المرجع. أرسلها، وتأكد من الشارة والوسم ومن أن البوت بدأ بتفاصيل العرض.
3. الرسالة المعبأة من عنوان العرض والمرجع وحدهما (140 حرفاً)، والشارة الحمراء «المرجع حُذف من الرسالة» تعني أن ميتا غيّرت النص. الحد 2000 رمز ورابط للرقم: تنبيه من 1800 ورفض عند 2000. الصور: PNG للطباعة، وSVG يُنزَّل مرفقاً فقط.
4. «اطبعه على البطاقة» يضع الرمز في تذييل بطاقة A4 ويجعلها قديمة فتُعاد. الرموز العامة (ملصق المكتب) من إعدادات الواتساب. حذف رمز يوقف المطبوع منه عن فتح رسالة معبأة، وإغلاق العرض لا يحذف رموزه: البوت يعتذر ويعرض البدائل.

العلم `offer_story_card` (مطفأ): «توليد» ثم «⬇️ تنزيل للنشر» في تبويب المشاركة، لعرض يقرؤه البوت وحده، والتنزيل يعيد التوليد إن قدُمت. البيانات من القائمة البيضاء نفسها التي يقرؤها البوت (لا وكيل ولا تكلفة ولا مقاعد ولا جدول فنادق). تحقّق في WhatsApp Manager هل يمكن النشر من رقمنا؛ إن كان على Cloud API وحده فالنشر من رقم آخر للوكالة يحدده المالك.
- **التراجع:** الأعلام إلى off من الإعدادات فوراً. الرموز المطبوعة تبقى تفتح المحادثة، والرسالة تصل نصاً عادياً يرد عليه البوت. الجداول والأعمدة إضافية بلا أثر.

## البث اللحظي الآمن للصندوق (E28، على مراحل)

رسالة العميل تظهر للموظف المخوّل خلال ثانيتين بدل 15 ثانية من الاستطلاع، على Reverb القائم في الحاوية. لا نداء لميتا، ولا هجرة. حدث البث يحمل رقم المحادثة ونوع التغيّر فقط (`{c, k}`)، ويصل قناة `user.{id}` الخاصة لمن يرى المحادثة لحظة الحدث بقواعد سياج المحادثات نفسها. الواجهة تعيد الجلب من المسارات المسيّجة.

قبل النشر: وسم الصورة الحالية `docker tag nuskjo-nuskjo-app:latest nuskjo-nuskjo-app:pre-e28`. والنسخة اليومية تكفي، فلا هجرة.

ما يعمل عند النشر بلا علم:
- **النشر الداخلي:** الخادم ينشر إلى Reverb داخل الحاوية (`REVERB_PUBLISH_*` في compose: ‏127.0.0.1:8080 عبر http) بمهلة اتصال ثانية ومهلة طلب ثانيتين، لا عبر النفق. Reverb يستمع على 127.0.0.1 وحده. المتصفح يبقى على `VITE_REVERB_*`.
- **إغلاق `/apps`:** nginx يرد 404 على واجهة النشر في Reverb، والمقبس للمتصفح على `/app/` وحده.
- **الأصل والسقوف:** Reverb يقبل مضيف `REVERB_ALLOWED_ORIGINS` وحده (في compose ‏`nuskjo.grade.sbs`، وافتراضياً مضيف APP_URL)، بسقف 200 اتصال، وحد 60 رسالة في الدقيقة لكل اتصال، ولا أحداث من المتصفح.
- **`/broadcasting/auth`:** خلف الدخول والجلسة والحساب النشط وحارس المسارات، وحد 60 في الدقيقة لكل مستخدم و120 لكل عنوان. القنوات `user.{id}` لصاحبها و`staff` لأي موظف نشط. لا قناة عامة.
- **شجرة الحسابات وقائمة الوكلاء** تتحدثان على القناة الخاصة `staff` بدل القناة العامة. نشر الواجهة والخادم معاً.
- **حد الإرسال:** 30 رسالة في الدقيقة لكل موظف (الرد والسعر وطلب الرقم)، ثم «تمهّل قليلاً». القيمة `WA_SEND_PER_MINUTE`.
- **محادثة عميل بلا رقم** (اسم مستخدم) صارت ظاهرة لمختص وسمها حين توجد أرقام إدارة، كبقية المحادثات.

بعد النشر مباشرة، بالترتيب:
1. إشعار حقيقي للجرس (مثلاً توكيل محادثة لموظف). يصل لحظياً: هذا دليل النشر الداخلي.
2. `curl -s -o /dev/null -w '%{http_code}' https://nuskjo.grade.sbs/apps/x` يعيد 404.
3. في devtools (Network › WS): اتصال `wss://nuskjo.grade.sbs/app/...` يعيد 101، و`POST /broadcasting/auth` يعيد 200، ولا اشتراك في قناة عامة.
4. اتصال من أصل غريب يُرفض: `wscat -c "wss://nuskjo.grade.sbs/app/<key>?protocol=7" -H "Origin: https://evil.example"` يعطي خطأ أصل.
- إن انقطع الجرس: `REVERB_ALLOWED_ORIGINS='*'` مؤقتاً في `/opt/nuskJO/.env` ثم `docker compose up -d --force-recreate nuskjo-app`، وراجع `storage/logs/reverb*.log`. وإن بقي، الصورة `pre-e28`.

العلم `inbox_realtime` (مطفأ)، بعد يوم نظيف من النشر. يعمل في الصندوق الجديد (`inbox_v2`) وحده:
1. فعّله من الإعدادات في ساعة هادئة.
2. أرسل رسالة من هاتف الاختبار إلى محادثة موسومة: تظهر في صندوق مختصها خلال ثانيتين بلا استطلاع، ولا تظهر لموظف من اختصاص آخر صندوقه مفتوح.
3. `docker compose restart nuskjo-app`: شريط «التحديث اللحظي متوقف» في الصندوق، ثم يختفي وتتحدث القائمة عند العودة.
4. راقب يومين: `rt.broadcast_failed` في سجل الواتساب يجب أن يبقى نادراً (القاطع يوقف البث 60 ثانية بعد كل فشل، والاستطلاع يعمل)، و`docker stats` لـ Reverb، وغياب شكاوى «محادثة ظهرت لغير مختصها».
- الاستطلاع يبقى احتياطاً: كل 60 ثانية والمقبس متصل، وكل 15 ثانية منقطعاً.

العلم `connection_resilience` (مطفأ):
1. فعّله. صفحة بعد النشر بملفات قديمة تُعاد تحميلها مرة واحدة (حارس 30 ثانية)، وفوق نموذج غير محفوظ يظهر «تحديث متاح» بدلها.
2. 502 أو 504 أو 52x أثناء النشر: شريط واحد «النظام يُعاد تشغيله أو غير متاح — سنحاول تلقائياً» بدل نافذة بصفحة البوابة، ويختفي وحده حين يجيب `/up`.
3. إرسال مجهول النتيجة (مهلة أو انقطاع بعد بدء الإرسال، أو 504 أو 524 في المتصفح): «قد تكون الرسالة أُرسلت — راجع المحادثة قبل الإعادة» بلون كهرماني، والخادم يرد 202 `OUTCOME_UNKNOWN`. المسودة باقية، والإرسال معطّل 10 ثوانٍ، والإعادة بالمفتاح نفسه لا تكرر رسالة خرجت مع `send_ledger`. الرفض الصريح يبقى «تعذّر الإرسال».
4. خطأ في مكوّن صفحة: بطاقة «حدث خطأ في هذه الصفحة — أعد التحميل» بدل الصفحة البيضاء.
- **التراجع، الأخف أولاً:** العلمان إلى off وقت التشغيل (الصندوق يعود للاستطلاع كل 15 ثانية فوراً). ثم قيم البيئة في `/opt/nuskJO/.env` (`REVERB_ALLOWED_ORIGINS='*'`) مع `--force-recreate`. ثم الصورة `pre-e28` أو `git revert` ثم `up -d`. القناة الخاصة `staff` لا تُرجَع إلا بنشر الواجهة والخادم معاً.

## صحة القناة كآلة حالات (E22، على مراحل)

حالة رقم الشركة عند ميتا في بطاقة «صحة القناة» (الإعدادات › صحة النظام والقناة)، والتفاصيل في `docs/whatsapp/channel-health.md`. ما يعمل عند النشر بلا علم:
- **الهجرة `2026_10_14_000022`** إضافية: ثمانية أعمدة `wa_health_*` وجدول `wa_account_events`. خذ قبلها لقطة: `SELECT wa_suspended, wa_suspended_source FROM wa_bot_settings`.
- **قفل آلي قائم** (مصدره `meta_event` أو `graph_error`) تنقله الهجرة إلى «محجوبة» (المصدر legacy) دون أي لحظة إرسال. يُرفع بعدها من البطاقة بزر «ارفع القفل»، لا من الإيقاف الطارئ. الإيقاف اليدوي ووضع الاستعادة يبقيان كما هما.
- **«محجوبة» تمنع دائماً**، حتى والعلم مطفأ. والبوت لا يستدعي النموذج، ويرفع «⛔ القناة محجوبة» على المحادثة.
- **فحص الصحة** يحفظ وقت آخر فحص والجودة في الوضعين، ولا ينقل الحالة إلا بالعلم.

العلم `channel_health` (مطفأ = الإيقاف الآلي القديم كما هو):
1. قبله: اضبط `WA_WABA_ID` وقارنه بالمكتشف في «ربط قناة ميتا». وتأكد أن رمز System User يحمل `whatsapp_business_management`.
2. فعّله في ساعة هادئة، ثم `docker exec nuskjo-app php artisan whatsapp:health-status`. تنتقل البطاقة من «لم تُفحص بعد» إلى «تعمل»، وتظهر مطابقة حساب الأعمال.
3. من لوحة ميتا اشترك في `account_alerts` و`security` و`business_capability_update` و`phone_number_name_update` (بقرار المالك). بعد ضبط WA_WABA_ID اضغط Test على `account_alerts` وحده، فيظهر صف «معلومة» في سجل أحداث ميتا. لا تضغط Test على `account_update` قبل ضبط المعرّف.
4. راقب أسبوعين: سجل أحداث ميتا والتنبيهات، والهدف صفر حجب كاذب. وسطور `health.transition` و`health.transition_refused` في سجل الواتساب.

بقرار المالك بعد المراقبة:
- `channel_health_block_on_token`: منع الإرسال عند الرمز الباطل (المقترح بعد أسبوعين).
- `integrity_breaker_lock`: قاطع النزاهة يحجب بدل التنبيه (المقترح بعد شهر بلا إنذار كاذب). العتبة والنافذة في `WA_INTEGRITY_THRESHOLD` و`WA_INTEGRITY_WINDOW_MINUTES`.
- **التراجع:** الأعلام الثلاثة إلى off من الإعدادات فوراً، فيعود الإيقاف الآلي القديم. حجب قائم يبقى ويُرفع من البطاقة بسبب. الأعمدة والجدول تُترك، فلا يُشغَّل `migrate:rollback`.

## رسائل الموظف الصوتية (E34، على مراحل)

يسجّل الموظف من الصندوق رسالة صوتية حتى دقيقتين، ويعاينها، ثم يؤكد المستلم ويرسلها. تصل العميل رسالة صوتية أصلية بأيقونة الميكروفون وزر تشغيل: ملف ogg/opus أحادي مرفوع بالمعرّف، بحمولة `type=audio` و`voice=true`. الطريق هو مسار الملفات نفسه (E32): الطلب يحوّل التسجيل ويحفظ نسخته ويحجز صفه ويرد 202، والرفع إلى ميتا في الطابور `wa-media-out`. ما يتغيّر عند النشر بلا علم:
- **الصورة** تضيف `ffmpeg` (ومعه ffprobe ومرمّز libopus). تتطلب إعادة البناء. سجّل فرق الحجم بـ `docker image ls` قبل وبعد. `scripts/smoke.sh` يتحقق من وجوده بعد النشر.
- **لا هجرة.** أعمدة `media_*` موجودة، والحالة played من E21.
- **ترويسات المتصفح:** `Permissions-Policy` صارت `microphone=(self)`، فالإذن لصفحاتنا وحدها ولا يحصل عليه إطار مضمّن. وCSP تضيف `media-src 'self' blob:` للمعاينة والمشغّل.
- **مجدول جديد:** `whatsapp:voice-tmp-sweep` كل ساعة (الدقيقة 35). يحذف من `storage/app/tmp/voice` ما بقي أكثر من ساعة، ويطبع العدد.
- **whatsapp:doctor** يطبع «ffmpeg: متاح» مع الإصدار، وأعداد اليوم: التحويلات ومتوسط زمنها، و«مشغول» (503)، والفشل. ومع العلم بلا ffmpeg يظهر خطأ `FFMPEG_MISSING`.
- **مسار المرفقات:** الصوت المؤرشف يُخدم بدعم Range (المشغّل يعرف المدة ويتنقل)، بالترويسات والتدقيق نفسيهما.
- **الحالة played** تظهر «▶️ سُمعت» بدل «شُغّلت».
- **قبل النشر:** `backup:run --reason=manual --label=pre-e34`، ووسم الصورة الحالية `pre-e34`.

الأعلام بالترتيب (من إعدادات الواتساب، أو `WA_FEATURE_<KEY>` للطوارئ؛ كلها مطفأة)، كلٌّ في ساعة هادئة:
1. **`staff_voice_notes`.** قبله: `docker exec nuskjo-app ffmpeg -version`، و`whatsapp:doctor` يقول «ffmpeg: متاح»، و`curl -sI` على صفحة الدخول يُظهر `microphone=(self)`. ثم يسجّل المدير رسالة قصيرة إلى رقمه الشخصي في نافذة مفتوحة: من Chrome، ثم Safari على iPhone، ثم Firefox. المتوقع: أيقونة الميكروفون وزر تشغيل عند العميل، والصف «قيد الإرسال» ثم «أُرسلت» ثم «▶️ سُمعت» بعد التشغيل. راقب أسبوعاً: سطور `wa.voice.converted` و`wa.voice.busy` و`wa.voice.failed` في سجل الواتساب، وأعداد doctor، و`docker stats nuskjo-app` أثناء عشرة تحويلات متتالية (التحويل أقل من ثانية لدقيقتين).
2. **`staff_voice_transcript`** بعد أسبوع بلا 503 متكررة، وبعد «تأكيد الطبقة المدفوعة» لمفتاح Gemini (E29). يظهر النص تحت الفقاعة للزملاء خلال دقيقة، ويُحسب في الاستهلاك بالمصدر `voice_out` خارج الرد الحي. لا يصل العميل أبداً. مع Claude لا تفريغ، لأنه لا يقبل الصوت.
3. **الحذف من ميتا (اختياري):** أضف `audio` إلى `WA_OUTBOUND_REMOTE_DELETE_TYPES` و`played` إلى `WA_OUTBOUND_REMOTE_DELETE_STATUSES`.

قرارات المالك (الافتراضي بين قوسين): ffmpeg في الصورة (نعم؛ البديل ترميز WASM في المتصفح)؛ من يرسل الصوت (كل من يملك `whatsapp.reply`)؛ التفريغ عبر Gemini (علم مستقل مطفأ)؛ الحد الأقصى `WA_VOICE_MAX_SECONDS` (120)؛ مدة الاحتفاظ بنسخ الصوت (سياسة المرفقات نفسها `WA_MEDIA_RETENTION_DAYS`). التشغيل والأعطال في docs/whatsapp/voice-notes.md.
- **التراجع:** العلم إلى off من الإعدادات، أو `WA_FEATURE_STAFF_VOICE_NOTES=false`، يخفي الزر ويرد المسار 404. ما في الطابور لحظتها يُرسل لأن موظفاً أكّده. ثم الصورة `pre-e34` للضرورة. الصفوف الصوتية المرسلة تبقى سجلاً صحيحاً، ولا بيانات تحتاج إرجاعاً.

## الرد المقتبس والتفاعلات والتصحيح والموقع وبطاقات الاتصال (E33، على مراحل)

أنواع رسائل Cloud API الرسمية وحدها، داخل نافذة الـ24 ساعة وعبر `WhatsAppChannel` بأقفاله كلها، وبلا قوالب. لا تعديل ولا حذف لرسالة صادرة في واتساب الرسمي: «التصحيح» رسالة جديدة مقتبسة من الخاطئة، والأصل يبقى كما هو. ما يعمل عند النشر بلا علم (تصحيح خلل):

- **رسالة لا تدعمها منصة ميتا** (تعديل العميل لرسالة، أو استطلاع، أو وسائط لم تكتمل) تصل بنص عربي واضح. لا يرد عليها البوت، وتصير «تدخّل» بسبب «🧩 رسالة غير مدعومة» مع إشعار واحد كل 30 دقيقة.
- **بطاقة جهة الاتصال الواردة** بالاسم وحده في النص، فلا يصل رقم الطرف الثالث إلى مزوّد الذكاء ولا معاينة المحادثة ولا إشعار الجوال. الرقم في الخيط لمن يملك الرد وحده، والتصدير بالاسم. وسطر في /privacy.
- **تفاعل الموظف ليس رداً:** لا يُسقط رد البوت الجاري ولا يمنع رسالة العطل.
- **الهجرة `2026_10_14_000033`** إضافية: جدولان جديدان `wa_places` و`wa_contact_cards`، ولا تمس أي جدول قائم. صفحة «📍 المواقع وبطاقات الاتصال» (رابطها في «🧰 الأدوات» بالإعدادات، لصاحب whatsapp.settings) تعمل قبل الأعلام لتعبئتهما.
- **قبل النشر:** `backup:run --reason=manual --label=pre-e33`.

الأعلام (من إعدادات الواتساب، أو `WA_FEATURE_<KEY>` للطوارئ؛ كلها مطفأة)، كلٌّ في ساعة هادئة على نسك:
1. `wa_reply_quote` ثم `wa_staff_reactions`: «⋯» بالمرور على الرسالة، وضغط مطوّل على الجوال: «↩️ رد» و«😀 تفاعل» و«✏️ إرسال تصحيح». جرّب مع هاتف الاختبار: رد مقتبس، وتفاعل ✅ ثم إزالته، وتصحيح لرسالة. راقب أسبوعاً `wa_bot_usage` بحثاً عن ردود ضاعت بعد تفاعل موظف، وسطر `wa.send.context_dropped` في سجل الواتساب: اقتباس رفضته ميتا فأُعيد مرة بلا اقتباس. سجّل رمز ميتا الفعلي لأول اقتباس مرفوض؛ إن لم يكن 131009 أو 100 فالشرط يحتاج ضبطاً.
2. `wa_share_cards` بعد تعبئة المواقع والبطاقات بموافقة مكتوبة من صاحب كل رقم: زرّا «📍 موقع» و«👤 بطاقة» فوق المنشئ بتأكيد يسمّي العميل. كل دبوس أو بطاقة رسالة خدمة مدفوعة.
3. بقرار المالك: أداتا البوت «إرسال دبوس موقع المكتب» و«إرسال بطاقة اتصال معتمدة» من «🧰 الأدوات»، وهما مطفأتان. المكتب الافتراضي «مسموح للبوت» شرط للدبوس، والدبوس ثم نص البوت رسالتان مدفوعتان.
4. أخيراً `wa_link_preview` إن أراده المالك: خانة «معاينة الرابط» في رد الموظف للروابط العامة وحدها. مضيفنا وخوادمنا المشتركة (`WA_PREVIEW_BLOCK_HOSTS`، grade.sbs افتراضياً) والروابط الموقّعة والمؤقتة لا تُعاين أبداً، والبوت لا يعاين.

قرارات المالك (الافتراضي بين قوسين): قائمة تفاعل الموظف `WA_STAFF_REACTIONS` (✅ 👍 🙏 ❤️ 👀)؛ بطاقة من البوت (لا)؛ دبوس المكتب من البوت (لا)؛ معاينة الروابط (مطفأة).
- **التراجع:** العلم المعني إلى off فوراً، والبيئة `WA_FEATURE_*=false` تتقدم. الجدولان لا يضران الكود القديم، و`git revert` ثم النشر للضرورة. لا استعادة للنسخة إلا إن ثبت تلف من الهجرة.

مبني ومطفأ كله. **لا يُفعَّل أي علم قبل قرار مكتوب من المالك في CHANGELOG لكل مسار على حدة.** التفاصيل في `docs/whatsapp/calls.md` و`docs/whatsapp/coexistence.md`.

4. الربط عبر Embedded Signup v4 في نافذة صيانة معلنة، بعد نسخة احتياطية وإعلان للموظفين. ثم `coexistence_echoes`.
5. تحقق يدوياً: أرسل من التطبيق نصاً وصورة، ثم عدّل واحذف. يظهر كل ذلك بوسم «📱 من هاتف الوكالة»، ويتوقف البوت، ولا تنفتح النافذة، والأصل باقٍ.
6. **التراجع البرمجي:** إطفاء `coexistence_echoes` مع إبقاء `coexistence_guard`. فك التعايش نفسه عبر المزوّد ودعم ميتا، لا عبر Deregister API.

3. `ops_alerts`: التنبيهات للمدراء (الجرس وFCM). تحقق بمهمة متأخرة تجريبية أو بانتظار تنبيه حقيقي.
4. `failures_center`: صفحة «🧯 الإخفاقات» للمدير. افتحها بالجوال وبالحاسوب. ثم `failures_redrive` بعد مراجعة أول رسائل فاشلة.
5. `analytics_v2`: التحليلات بفترات وتبويب «📈 الحركة» وبطاقة «💵 تكلفة ميتا». قارن أرقام 30 يوماً بالقديمة قبل اعتمادها.
6. `quote_export`: «⬇️ تصدير CSV» في طلبات التسعير لمن يملك `quotes.export` (المدير وحده). منح المحاسب بقرار المالك بسكربت موجّه، لا بالبذرة. جرّب تصدير شهر وافتحه في Excel.
7. `meta_analytics_reconcile` بقرار المالك (يحتاج WA_WABA_ID)، و`ops_tick` بعد قياس `docker stats --no-stream nuskjo-app` قبله وبعده.
8. المراقب الخارجي على `/up` بقرار المالك، واختباره بإيقاف المجدول في وقت هادئ (docs/whatsapp/ops-alerts.md).

- **التراجع:** الأعلام إلى off من الإعدادات فوراً (التنبيهات تعود تسجيلاً، والصفحة 404، والتحليلات القديمة). إفراغ `OPS_METRICS_TOKEN` يغلق المقاييس، وسحب `quotes.export` يوقف التصدير. الأعمدة والفهارس تُترك، فلا يُشغَّل `migrate:rollback`. وإن سبّب فهرس بطئاً يُحذف وحده بـ `DROP INDEX IF EXISTS` بعد نسخة وبإذن المالك.

## الاختيارات التفاعلية وقائمة العروض ونموذج طلب التسعير (E36، على مراحل)

قوائم وأزرار رسمية من Cloud API، يبنيها الخادم من بيانات العروض بمعرّفات يولّدها هو ويتحقق منها عند النقر. نص البوت والقائمة رسالة واحدة. وزرّا «✅ تأكيد» و«✖️ إلغاء» لمعاينة المساعد الإداري، ونموذج Flow ثابت لطلب التسعير بلا نقطة نهاية. لا كتالوج ميتا. التفصيل في `docs/whatsapp/interactive-choices.md`.
- الهجرة `2026_10_14_000036` إضافية: جدول `wa_choice_sets` (يُقلَّم بعد 30 يوماً)، وعمودان في الإعدادات (`wa_quote_flow_id` فارغ، و`wa_quote_flow_mode` بقيمة published). لا يتغير شيء للعميل بعدها.
- ما يعمل بلا علم (تصحيح وأمان):
  - نقرة على خيار أرسله البوت تُتحقق دائماً، فقائمة أُرسلت قبل إطفاء العلم تُرفض بأمان.
  - زر المعاينة القديم لا يؤكد إجراءً أحدث، وعنوانه لا يمر بالتأكيد النصي.
  - طلب من كتالوج ميتا أو سؤال عن منتج فيه يصل موظفاً بسبب «🛒 طلب من الكتالوج»، ولا يرد عليه البوت.
  - سطر جديد في /privacy.
- الأدوات الثلاث (`show_offers_menu` و`present_choices` و`send_quote_form`) مطفأة في «🧰 الأدوات» حتى بعد الأعلام.
- **الكلفة:** كل رسالة تفاعلية رسالة خدمة مدفوعة بعد الشريحة المجانية. النص والخيارات رسالة واحدة، إلا نصاً أطول من حد ميتا.

التفعيل، كلٌّ في ساعة هادئة على نسك:
1. نسخة `backup:run --reason=manual --label=pre-e36`، ثم النشر والهجرة.
2. `admin_confirm_buttons` أولاً (خطره داخلي). من رقم إدارة: اطلب إضافة معلومة، فتصل المعاينة بزرين. جرّب «✅ تأكيد»، ثم معاينة جديدة وزر المعاينة السابقة (يرد «انتهى أو تغيّر»)، ثم «✖️ إلغاء»، ثم كتابة «تأكيد». راقب أسبوعاً `wa_admin_actions` (التنفيذ بالزر يُختم «(بالزر)»، والزر القديم `admin_confirm` مرفوضاً).
3. `interactive_choices` على محادثة المدير التجريبية وحدها: `WA_INTERACTIVE_PILOT_CONVERSATIONS=<رقم المحادثة>` ثم `config:cache`، وفعّل الأداتين من «🧰 الأدوات». من الهاتف (Android وiOS):
   - «ما عروضكم؟» تأتي قائمة واحدة بنص البوت، والعناوين والأسعار من العروض.
   - اختر عرضاً، ثم الفندق والغرفة وأزرار الحجز، ثم «احجز هذا»: طلب الحجز بالعرض والخيار والغرفة نفسها.
   - انقر قائمة قديمة بعد أحدث منها: يرد البوت بأن القائمة تغيّرت.
   - في الخيط: حبوب الخيارات تحت رسالة البوت، وشارة «🔘 اختيار» خضراء أو كهرمانية.
   ثلاثة أيام، ثم احذف المتغير لتعميمها. راقب نسبة الاختيارات غير الصالحة (`wa.choice.resolved` في سجل الواتساب)، و`wa_bot_usage`، وعدد الرسائل، وسطر `wa.interactive.fallback` (رفض ميتا للتنسيق).
4. `quote_flow` بعد توثيق النشاط التجاري ونشر الـ Flow وضبط معرّفه (الخطوات في `docs/whatsapp/interactive-choices.md`): الوضع «تجربة» برقم الاختبار أولاً، ثم «منشور»، ثم فعّل أداة النموذج. تحقق: نموذج معبّأ يصنع طلب تسعير واحداً منقّى، ويصل العميلَ تأكيد برقم الطلب، وفي الخيط «📝 نموذج طلب تسعير» برابط الطلب.

قرارات المالك (الافتراضي بين قوسين): قائمة العروض بدل السرد النصي (تُعرض إن فُعّلت الأداة)؛ أزرار الحجز بعد البطاقة (نعم)؛ زرّا المساعد الإداري (موصى بهما)؛ النموذج (بعد التوثيق وبقرار مكتوب، وحقوله كما في الملف)؛ الكتالوج (لا، يحتاج قراراً مكتوباً منفصلاً).
- **التراجع:** العلم المعني إلى off فوراً، أو `WA_FEATURE_*=false` ثم `docker compose up -d`. القوائم المرسلة تُرفض نقراتها بأمان، والبوت يعود للسرد النصي و`request_quote`. الجدول والعمودان لا يضران الكود القديم، و`git revert` ثم النشر للضرورة. لا استعادة للنسخة إلا لتلف مثبت.

## كتيّبات التشغيل والتوثيق المحروس بالاختبارات (E25، على مراحل)

وثائق واختبارات في معظمها، والفهرس في `docs/README.md`. ما يتغيّر على الإنتاج عند النشر بلا علم:
- **`/.well-known/security.txt`** ملف نصي ثابت، بكتلة nginx تخدمه وحده قبل حجب الملفات النقطية. أي مسار آخر تحت `/.well-known/` يبقى محجوباً.
- **قسم «الإبلاغ عن ثغرة أمنية»** في `/privacy` بالعربية والإنجليزية، بمرساة `#security`.
- **لا هجرة.** والوثائق لا تدخل الصورة (`docs/` و`**/*.md` في `.dockerignore`)، وتدخل حاوية بوابة النشر. البوابة تستثني مجموعة `horizon` المرتبطة بالتاريخ، وتبقى في CI.

الخطوات:
1. نسخة `backup:run --reason=manual --label=pre-e25` ووسم الصورة الحالية `nuskjo-nuskjo-app:backup-pre-e25`.
2. انشر كالمعتاد، فالصورة تُبنى من جديد لكتلة nginx.
3. تحقق:
   - `curl -sI https://nuskjo.grade.sbs/.well-known/security.txt` يعيد 200 ونوعه `text/plain`.
   - `curl -sI https://nuskjo.grade.sbs/.env` و`https://nuskjo.grade.sbs/.well-known/x` ما زالا 403 أو 404.
   - `/privacy#security` ظاهر.
   - `docker run --rm --entrypoint sh nuskjo-nuskjo-app -c 'test -e /var/www/html/docs && echo LEAK || echo OK'` يطبع OK.
4. **العلم `alert_runbook_refs`** في ساعة هادئة: تنتهي تنبيهات المدراء بـ « — الكتيب RB-NN». لا إشعار تجريبي في الإنتاج: يكفي أول تنبيه حقيقي، والاختبار في CI.
5. للمالك: تفعيل GitHub Private vulnerability reporting وSecret scanning push protection من Settings › Code security، واعتماد البريد الأمني ومهل الاستجابة في `docs/RISKS.md`، وتجديد `Expires` في `security.txt` قبل 2027-09-30.

- **التراجع:** العلم إلى off يعيد نص التنبيهات كما كان. وإن عطّلت كتلة `/.well-known/security.txt` شيئاً فتُحذف وحدها من `docker/nginx.conf` ثم يُعاد البناء. وإلا `git revert` ثم `scripts/deploy.sh`. لا شيء في القاعدة.

## مغادرة موظف

بالترتيب، في اليوم نفسه:
1. **المستخدمون:** عطّل الحساب (لا تحذفه، فسجل التدقيق يبقى مرتبطاً به). يخرج من كل أجهزته فوراً، وتتوقف إشعاراته.
2. **أرقام الإدارة في الواتساب:** رقمه المرتبط بحسابه يُعامَل كعميل تلقائياً بعد التعطيل؛ احذفه أو عطّله من الصفحة مع ذلك.
3. **المحادثات المسندة إليه:** انقلها لزميل من صندوق الوارد، وأزل اختصاصاته من «توجيه المواضيع». `whatsapp:fence-report` يُظهر ما بقي موكلاً له.
4. **مفاتيح خارج النظام:** إن كان يملك وصولاً إلى الخادم أو لوحة ميتا أو Cloudflare أو مدير كلمات المرور، اسحبه وغيّر ما رآه من أسرار.
5. إن كان مديراً: تأكد من بقاء مدير نشط آخر (النظام يمنع تعطيل آخر مدير).
