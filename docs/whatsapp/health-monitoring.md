# الصحة والمراقبة

من يعرف أن شيئاً تعطّل، وبأي إشارة، وأين التفصيل. هذه الوثيقة خريطة تحيل إلى وثيقة كل جزء ولا تكررها.

## لماذا وُجد

كان فحص Docker يطلب الصفحة الرئيسية، فيأخذ تحويلاً إلى صفحة الدخول ويعدّه نجاحاً والعامل ميت. ومع البوابة صار لكل رقم جلسة قد تعلق وهي «ready». فصار لكل عطل إشارة مقيسة لا حالة محفوظة، ولكل إشارة تنبيه واحد، ولكل تنبيه كتيّب.

## القواعد الثابتة

- **التنبيه لا يمر عبر واتساب:** الجرس وإشعار الجهاز، لأن الرقم نفسه قد يكون المعطّل.
- **نص التنبيه بلا رقم عميل ولا نص رسالة:** أعداد ورموز وأسماء طوابير وأسماء أرقامنا.
- **حالة رقم لا تُسقط `/up`:** الحاوية سليمة والرقم منقطع شيئان مختلفان. وكذلك البوابة: لها فحص Docker خاص (`/api/health/ready`).
- **الجاهزية فحص حقيقي:** رقم بلا فحص ناجح خلال 5 دقائق غير جاهز، أياً كانت حالته المحفوظة ([channel-health.md](channel-health.md)).
- **طابور التكاملات خارج فحص المتأخر:** طرف خارجي متوقف لا يُسقط `/up`.

## نموذج التهديد (عام)

- **تنبيه يكشف بيانات عبر طرف ثالث (FCM):** نص ثابت بلا بيانات عميل.
- **إغراق المدير بالتنبيهات حتى يتجاهلها:** كبح بالمفتاح ساعة لكل رقم ونوع، و«عاد طبيعياً» مرة واحدة.
- **مقاييس مكشوفة:** `/internal/metrics` (E24) مغلق بلا رمز، وتسمياته من قوائم ثابتة.

## ما لا تضمنه الطبقة

- أي تنبيه داخلي حين تتوقف الحاوية كلها أو النفق: هذا عمل المراقب الخارجي.
- معرفة سبب الحظر أو موعد رفعه: على هاتف الرقم وحده (RB-03).
- رد إنسان في المهلة: المهل في مصفوفة الاستجابة في [../RISKS.md](../RISKS.md)، والتنفيذ تشغيل.
